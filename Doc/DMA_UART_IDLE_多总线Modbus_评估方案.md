# 多总线 Modbus（RTU）DMA + 串口空闲中断（IDLE）评估方案

日期：2026-05-16  
目录：`D:\Data\硬件\单片机资料20241128\2，水质仪器单片机源代码及固件、设计说明书\备份\bug解决`  
工程：`0429重新/nanoWAys20240724改单片机+测润泽`

## 1. 背景与目标

当前工程存在 3 条 Modbus-RTU 从站总线（多串口并行）：

- MB1：USART1
- MB3：USART3
- MB6：USART6

工程按 `修改说明.txt/guide.txt` 的思路做了“多总线寄存器组分离/独立映射”后，出现“运行一段时间卡死，最终触发 IWDG 复位”的问题。该问题已在代码侧做过一轮修复（见 `Modbus_MB3_卡死复位_越界排查记录.md`），但为了降低长期运行风险，并提升多总线下的实时性与抗干扰能力，需要评估是否将串口通信升级为：

- **RX：DMA + 串口空闲中断（IDLE）**（或 DMA + HT/TC）  
- **TX：DMA（可选）** + TC/发送完成回调驱动 RS485 DE 翻转

评估目标：

1) 降低“阻塞等待/中断风暴/任务饿死”导致的喂狗失败风险  
2) 提升多总线并发时的吞吐与实时性（降低 CPU 占用）  
3) 保持 Modbus-RTU 帧边界识别准确性（避免“IDLE 误判帧结束”）

## 2. 现状（与 DMA 相关的事实）

- 工程里 **USART1（MB1）当前未启用 DMA**（Keil 编译实际引用 `Src/usart.c`，仅 NVIC/中断接收路径）。  
- USART3/USART6 在 `Src/usart.c`/CubeMX 生成代码中存在 DMA 初始化段，但现有 Modbus port 层仍以中断+软件缓冲方式为主（并非“彻底 DMA 化”）。

结论：如果要引入 DMA+IDLE，需要对 **portserial/串口 ISR/缓冲区管理/RS485 方向控制**做一套更一致的改造，而不是“只开 DMA 开关”。

## 3. 为什么 DMA + IDLE 可能会更好

### 3.1 可能改善的点

- **降低 ISR 频率**：由“每字节中断”变为“DMA+IDLE/半满满中断”，CPU 占用显著下降。  
- **抗干扰更强**：短时间的噪声/毛刺不会导致大量字节中断把系统拖死（尤其多总线并发时）。  
- **更容易做统计与超时处理**：DMA 写入计数可以直接反映“近一段时间收到多少字节”，利于定位线缆干扰、波特率不匹配、RS485 方向异常等问题。  
- **更利于多总线共存**：三路串口同时收数据时，DMA 将接收搬运从 CPU 侧挪走。

### 3.2 但它不会自动解决所有卡死

卡死/IWDG 的常见根因并不只有“CPU 忙不过来”，还包括：

- **数组越界/内存破坏**（示例：MB3 holding/input 缓冲区小于 `REG_*_NREGS` 导致越界，进而随机卡死）  
- **互斥锁死等**（某路径持锁未释放，导致多总线任务阻塞）  
- **等待发送完成（TC）无限循环**（RS485 DE 翻转依赖 TC，如果 TC 标志逻辑不严谨会永久等待）  
- **UART 错误标志未清除导致“中断风暴”**（ORE/FE/NE/PE）  

因此：DMA+IDLE 是“降低系统被拖死概率”的工程化手段，但仍需要配合边界检查、超时、错误清除等策略。

## 4. Modbus-RTU 的关键点：IDLE 不等价于 t3.5

Modbus-RTU 帧结束判断来自“总线静默时间” t3.5（约 3.5 个字符时间），而 UART 的 **IDLE 中断触发条件**是“接收线在 1 个字符时间左右的空闲”，两者不严格等价。

这带来两个风险：

1) **误判帧结束**：主站在帧内出现短暂空隙（极端情况/抖动/干扰）时，IDLE 可能提前触发。  
2) **帧粘连**：IDLE 触发得晚或不触发时（持续字节流），需要靠 t3.5/定时器来切分帧。

推荐原则：

- 把 **IDLE** 当作“快速通知：RX 暂时停了，可以取 DMA 缓冲区里的新数据”。  
- 把 **t3.5 定时器（或等价逻辑）**当作“最终帧边界判决”。  

也就是说：DMA+IDLE 之后，依然建议保留/强化 Modbus 的 t3.5 计时机制（或在 IDLE 后再启动一个 t3.5 确认）。

## 5. 推荐的落地方案（分阶段）

### Phase 0：先建立可观测性（不改通信机制也能做）

目的：复位仍发生时能快速判断是“阻塞/死循环/错误风暴/越界复发”哪一种。

建议增加（每路串口独立统计）：

- `uart_rx_idle_cnt`：IDLE 次数（后续 DMA 方案用）  
- `uart_err_ore_cnt/fe_cnt/ne_cnt/pe_cnt`：错误标志次数  
- `mb_wait_tc_timeout_cnt`：等待 TC 超时次数  
- `mb_mutex_timeout_cnt`：互斥锁超时次数  
- `mb_rx_overflow_cnt`：Modbus RX 软件缓冲区溢出次数（若保留 ring buffer）  

输出方式（二选一即可）：

- 映射到各自的 Modbus Input/Holding 寄存器（便于现场读取）  
- 或周期性打印（若现场有串口日志/RTT/SWO）

验收：出现复位前，至少能看到“哪类计数在飙升”。

### Phase 1：先做 RX DMA + IDLE（单路试点）

建议先试点 **USART3（MB3）**：

- 现状中 USART3 代码里更可能已有 DMA 初始化，改动小、风险可控  
- MB3 之前暴露过寄存器越界问题，试点时可顺带验证“长期稳定性”

实现建议（通用逻辑）：

1) **DMA RX Circular**，一个固定大小的 `rx_dma_buf[DMA_RX_SIZE]`（例如 256/512 字节）  
2) 在 `USARTx_IRQHandler` 中处理 `IDLE`：  
   - 清 IDLE 标志（读 SR/DR 或按 HAL/LL 要求清）  
   - 读取 DMA 当前写入位置（NDTR 反推写指针）  
   - 将“新增的数据段”拷贝/搬运到 Modbus 的 RX ring buffer（或直接给 Modbus stack 逐字节投递）  
3) 仍保留 Modbus t3.5 定时器/帧结束判定：  
   - 每次搬运新字节后刷新“最近收字节时间”，由 t3.5 到期触发 `EV_FRAME_RECEIVED`

关键设计点：

- **不要在 ISR 内做大量 memcpy**（DMA 缓冲区大时会拉长中断），建议只做轻量搬运或设事件让任务搬运。  
- 多总线下必须做到 **每路 UART 独立 DMA 缓冲区、独立写指针、独立统计**。

验收：

- 连续压测（主站高频读写、多路交叉访问）≥ 24 小时无 IWDG 复位  
- 统计计数合理：错误标志不会无限增长，互斥锁超时接近 0

### Phase 2：再扩到 USART6、USART1

扩展策略：

- **USART6（MB6）**：通常与 MB3 类似，按同方案推广  
- **USART1（MB1）**：现状未启 DMA，需补 DMA Init 与 IRQ 优先级校验

验收：三路同时压测 ≥ 24 小时无复位；CPU 占用下降（若可测量）。

### Phase 3（可选）：TX DMA

何时需要：

- 多总线下主站频繁写寄存器/写线圈，且每次发送都走“等待 TC/发送中断”，CPU 占用或阻塞风险仍高时。

关键点（RS485 常见坑）：

- **DE 拉高**：在启动 TX DMA 前置位  
- **DE 拉低**：必须等 **USART TC=1**（移位寄存器完全发送完）再拉低  
- 如果只等 DMA 传输完成（TC/HT）就拉低 DE，可能导致最后 1~2 字节被截断，主站表现为 CRC 错/超时重试

建议落地方式：

- TX DMA 完成后不立即拉低 DE，而是在 TC 中断/轮询（带超时）后拉低  
- 保留已加的 `WaitTC guard`（防止某些异常导致永久等待）

## 6. 风险评估与规避

### 6.1 中断优先级与 RTOS API

DMA IRQ/USART IRQ 若调用 CMSIS-RTOS2/FreeRTOS API，需要确保：

- `NVIC` 优先级满足“可在 ISR 中调用的最高优先级限制”  
- 或者 ISR 里只做 `flag + osSemaphoreRelease`（且该 API 在工程配置下允许在 ISR 调用）

规避：把“重逻辑（搬运/解析）”放到任务里，ISR 只负责“记录/唤醒”。

### 6.2 缓冲区大小与丢包

DMA RX buffer 太小，会在总线突发时覆盖未处理数据。建议：

- `DMA_RX_SIZE` 至少覆盖 **1 帧最大长度**（Modbus-RTU 最大 256 字节含地址/功能码/数据/CRC）  
- 更推荐 512（结合 RAM 情况）  

并配套：

- “搬运延迟上限”控制（任务要及时取走 DMA 数据）  
- `mb_rx_overflow_cnt` 指标可用于现场评估是否需要加大 buffer

### 6.3 IDLE 误判帧边界

规避：保留 t3.5 或“IDLE 后再等待 t3.5 确认”。避免用“IDLE 直接当帧结束”。

### 6.4 多总线寄存器映射的一致性

DMA 改造不会直接触碰寄存器映射，但多实例时必须确保：

- 轮询入口（如 `eMBxPoll`）在进入前设置“当前实例标识”（例如 `g_mb_inst=x`）  
- 任意共享变量（事件队列、状态机、缓冲区）都必须按实例隔离或正确加锁

## 7. 结论（建议）

建议采取“稳态优先、分阶段、先 RX 后 TX”的策略：

1) 先补齐统计与可观测性（Phase 0）  
2) 先在 MB3（USART3）上做 RX DMA + IDLE（Phase 1）验证稳定性  
3) 再推广到 MB6/MB1（Phase 2）  
4) 若仍有阻塞/CPU 压力，再评估 TX DMA（Phase 3）

DMA+IDLE 预计能明显降低多总线并发时的 CPU 压力与“中断风暴拖死系统”的概率；但它不是替代边界检查/超时/错误清除的万能解，仍需要与现有“WaitTC guard、互斥锁超时、UART 错误清除、事件竞态修复”等策略配套。

## 8. 根因举例（与本工程历史问题一致）

示例：某路总线的 Holding/Input 缓冲区长度小于协议栈宏定义的寄存器数量。

- 栈里定义：`REG_HOLDING_NREGS=512`  
- 但该总线独立映射文件里只分配了 `usRegHoldingBufX[110]`  
- 当主站访问 110 之后的寄存器时，栈会继续写入数组，造成 **越界写** → 破坏临近 RAM（可能是任务控制块、队列、互斥量、函数指针等）  
- 结果表现为：运行一段时间后随机卡死、最终喂狗失败触发 IWDG 复位

此类问题与是否使用 DMA 无直接关系，但 DMA 化后系统更“抗压”，能减少其它非确定性因素叠加导致的复位概率。
