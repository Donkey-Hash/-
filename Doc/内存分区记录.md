# 内存分区记录（STM32F407VET6 / nanoWAys 工程）

更新时间：2026-05-16  
工程路径（相对本目录）：`0429重新/nanoWAys20240724改单片机+测润泽`

本文档用于把“本工程约定的片内内存分区/地址规划”集中记录下来，方便后续排查 **程序升级、Boot 跳转、Flash 擦写、参数保存** 等问题。

> 说明：MCU 的物理内存结构由芯片决定；“分区”通常是工程在此基础上通过 **链接地址、固定地址变量、Flash 擦写策略** 约定出来的逻辑划分。

---

## 1. MCU 与工程配置概览

- 目标芯片：`STM32F407VET6`（见 `0429重新/nanoWAys20240724改单片机+测润泽/nanoWAys.ioc` 中 `Mcu.CPN`）
- Flash 物理基地址：`0x0800_0000`
- SRAM 物理基地址：`0x2000_0000`
- CCM SRAM 物理基地址：`0x1000_0000`（Keil 工程里以 IRAM2 形式出现）

### 1.1 Keil 工程里声明的 On-chip memory（用于链接/显示）

来自 `0429重新/nanoWAys20240724改单片机+测润泽/MDK-ARM/nanoWAys.uvprojx`：

- `IRAM`：`Start=0x20000000`，`Size=0x30000`（192KB）
- `IROM`：`Start=0x08000000`，`Size=0x100000`（1MB，**注意：该值与 VET6 常见 512KB Flash 存在不一致风险**）

### 1.2 Keil 下载算法（Program/Download）里使用的 Flash 容量

来自 `0429重新/nanoWAys20240724改单片机+测润泽/MDK-ARM/nanoWAys.uvoptx`（可看到使用 `STM32F4xx_512.FLM`，并带 `-FL080000`）：

- 下载/擦写按 `512KB` Flash 进行（`0x08000000` ~ `0x0807FFFF`）

## 2. 本工程约定的 Flash 分区（宏定义）

### 2.1 按扇区（sector）起始地址的映射

文件：`0429重新/nanoWAys20240724改单片机+测润泽/Bsp/inc/stm32flashmap.h`

（仅列出与 512KB 相关的常用扇区；该文件还定义了更大容量型号的 sector 12+ 地址）

- Sector0：`0x08000000`（16KB）
- Sector1：`0x08004000`（16KB）
- Sector2：`0x08008000`（16KB）
- Sector3：`0x0800C000`（16KB）
- Sector4：`0x08010000`（64KB）
- Sector5：`0x08020000`（128KB）
- Sector6：`0x08040000`（128KB）
- Sector7：`0x08060000`（128KB）

### 2.2 工程逻辑分区（Boot / Reserve / Data / App）

同文件：`0429重新/nanoWAys20240724改单片机+测润泽/Bsp/inc/stm32flashmap.h`

- Bootloader 区  
  - 起始：`ADDR_FLASH_BOOT = 0x08000000`  
  - 长度：`LENGTH_BOOT_FLASH = 0x10000`（64KB，覆盖 sector 0~3）
- Reserve/缓冲区  
  - 起始：`ADDR_FLASH_RESERVE = 0x08010000`  
  - 长度：`LENGTH_RESERVE_FLASH = 0x10000`（64KB，sector 4）
- Data/数据区（用户数据、参数等）  
  - 起始：`ADDR_FLASH_DATA = 0x08020000`  
  - 长度：`LENGTH_DATA_FLASH = 0x20000`（128KB，sector 5）
- App/应用区  
  - 起始：`ADDR_FLASH_APP = 0x08040000`  
  - 长度：`LENGTH_APP_FLASH = 0x40000`（256KB，覆盖 sector 6~7）  
  - 结束：`APP_END_ADDRESS = 0x0807FFFF`

### 2.3 “当前固件实际放置位置”的验证证据

`0429重新/nanoWAys20240724改单片机+测润泽/MDK-ARM/nanoWAys/nanoWAys.hex` 的第一条扩展线性地址记录为：

- `:020000040804EE`  

这意味着后续数据段的高地址为 `0x0804_xxxx`，对应 **应用固件链接/烧录起点在 `0x08040000` 附近**，与 `ADDR_FLASH_APP = 0x08040000` 的分区约定一致。

## 3. Data 区内部的“二级划分”（历史/兼容约定）

文件：`0429重新/nanoWAys20240724改单片机+测润泽/Bsp/inc/cpumemmap.h`

该文件中定义了另一套“更细的 Data 区切分”注释（位于 `0x08030000` 附近），并给出了示意：

- `FLASH_USER_DATA_START_ADDRESS = 0x08030000`
- 注释中的布局（节选）：
  - `0x0803 0000 - 0x0803 07FF`：Modbus Data 2KB
  - `0x0803 0800 - 0x0803 A7FF`：Device Data 40KB
  - `0x0803 A800 - 0x0803 AFFF`：Encrypt Data 2KB
  - `0x0803 B000 - 0x0803 FFFF`：Boot Data 20KB

> 注意：这套“二级划分”与 `stm32flashmap.h` 的“Data 区=sector5（0x08020000~0x0803FFFF）”并不矛盾，它更像是在 sector5 的后半段（`0x08030000`~`0x0803FFFF`）做功能区切片。

### 3.1 固定地址常量（device 参数表）的放置位置

文件：`0429重新/nanoWAys20240724改单片机+测润泽/Bsp/src/bsp/devicepara.c`

该文件使用 `__attribute__((at(0x0803xxxx)))` 把一些默认参数常量强制放到 Flash 固定地址，例如：

- `FlashDev1Para`：`0x08030800`
- `FlashDev2Para`：`0x08031000`
- ...
- `FlashDev20Para`：`0x0803A000`

这些地址都位于 `0x08030000`~`0x0803A000` 范围内，符合 `cpumemmap.h` 注释中 “Device Data” 的区间设想。

## 4. 用户数据/参数实际读写位置（工程代码用到的宏）

### 4.1 AllDevsData（包含 Modbus 数据缓冲区等）的保存地址

文件：`0429重新/nanoWAys20240724改单片机+测润泽/Bsp/src/FlashUserData.c`

该文件保存与读取使用的宏是：

- `ADDR_FLASH_ALL_DEVS_DATA`（见 `0429重新/nanoWAys20240724改单片机+测润泽/Bsp/inc/stm32flashmap.h`）
- 该宏当前定义为：`ADDR_FLASH_ALL_DEVS_DATA = ADDR_FLASH_DATA = 0x08020000`

也就是说：**运行时保存的 AllDevsData 数据块从 `0x08020000` 开始落在 sector5(Data 区) 内。**

## 5. 风险提示（建议在后续版本里统一）

1. `MDK-ARM/nanoWAys.uvprojx` 里声明的 `IROM Size=0x100000(1MB)` 与 `uvoptx` 中下载算法 `STM32F4xx_512.FLM / -FL080000(512KB)` 可能不一致。  
   - 如果代码/常量/固定地址区不小心超出 `0x0807FFFF`，链接阶段未必能及时暴露问题，但下载/运行会出异常。
2. sector5(`0x08020000`~`0x0803FFFF`) 同时承担了：
   - “运行时可写”的 `AllDevsData`（从 `0x08020000` 起写入）
   - “固定地址常量”的 `devicepara.c`（落在 `0x08030800` 等）
   - `cpumemmap.h` 注释中的多个功能区切片
   
   **如果擦写策略是按 sector 整擦（STM32F4 的常见做法），那么保存用户数据时擦 sector5 可能会破坏这些固定地址常量区。**  
   建议：后续明确 sector5 内各数据的生命周期与擦写策略，必要时把“可写数据区”和“固化常量区”拆到不同 sector。
